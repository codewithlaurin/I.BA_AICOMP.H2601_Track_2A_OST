# BM25 candidate retrieval and dense reranking

The query path is now:

`claim → BM25 top 50 → cosine reranking of those IDs → top 5 → Apertus`

Copy `scripts/sparse_index.py` and the updated `scripts/check_claim.py` into your
`track_2a/scripts/` directory. Keep the existing `apertus_nli.py`. No new dependency,
PDF parsing or embedding generation is required.

## Build the sparse index once

Run from `track_2a`, after vector indexing finishes:

```sh
uv run python scripts/sparse_index.py
```

This reads the exact passages already in the `voting_booklets_e5_v1` Qdrant
collection at `data/qdrant`. It saves one JSON BM25 index per booklet under
`data/bm25`. The JSON contains postings, term frequencies, chunk lengths, source
fingerprints and configuration. Repeat the command after modifying the vector
corpus; unchanged booklets are skipped. Run only one indexing process at a time.

To build just one booklet:

```sh
uv run python scripts/sparse_index.py --document-id SOURCE_SHA256
```

Replace `SOURCE_SHA256` with the actual hash from that booklet's `pages.json`.
Expect `Indexed: ... (N chunks)` initially, then `Unchanged: ...` on a repeat run.

## Check retrieval without an API call

```sh
uv run python scripts/check_claim.py "Die E-ID ist freiwillig." \
  --document-id SOURCE_SHA256 --dry-run --output data/results/hybrid-retrieval.json
```

Choose a claim about the selected booklet. Hybrid retrieval is the new default.
The result includes:

- `retrieval.candidates`: all BM25 candidates, with IDs, page numbers, BM25 ranks
  and scores before reranking.
- `retrieval.candidate_k`: requested pool size, default 50.
- `retrieval.candidate_count`: number of passages with lexical matches, capped at 50.
- `retrieval.bm25_config` and `corpus_sha256`: the sparse-index settings and snapshot.
- `evidence`: the final top five passages, their cosine scores, BM25 scores/ranks,
  original text and document/page provenance.

Inspect whether the known evidence occurs in the candidate list and whether it
survives into the final evidence list. Every final chunk must come from that list.

Compare with the preserved baseline:

```sh
uv run python scripts/check_claim.py "Die E-ID ist freiwillig." \
  --document-id SOURCE_SHA256 --retrieval dense --dry-run \
  --output data/results/dense-retrieval.json
```

Then run the classifier using the same hybrid retrieval:

```sh
uv run --env-file .env python scripts/check_claim.py "Die E-ID ist freiwillig." \
  --document-id SOURCE_SHA256 --candidate-k 50 --top-k 5 \
  --output data/results/hybrid-classification.json
```

Custom paths: `sparse_index.py` accepts `--db`, `--collection` and `--output`;
`check_claim.py` accepts matching `--db`, `--collection` and `--sparse-dir`.

## Implementation choices

BM25 uses `k1=1.2`, `b=0.75`, and positive IDF
`log(1 + (N - df + 0.5) / (df + 0.5))`. The term contribution is
`idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * length / average_length))`.
Here each chunk is a BM25 document; statistics are computed within the selected
booklet, matching our document-scoped query workflow. This is a small standard-library
inverted index with exact scoring, suitable for the current corpus size.

Tokenization applies Unicode NFKC normalization and case folding, then extracts
Unicode letters/numbers. It retains accents, numerals and negations (`nicht`, `pas`,
`non`). Apostrophes and hyphens split words consistently in queries and documents.
There is no stemming, stopword removal, German compound splitting, translation,
or query expansion. Repeated query terms count once. BM25 ties break by chunk ID.

The persisted postings are loaded without retokenizing documents. At query time,
the selected booklet's payloads are paginated from Qdrant and fingerprinted to check
freshness; this reads text/metadata but does not fetch every vector or rebuild BM25.
A changed text, ID set or metadata snapshot causes a visible stale-index error.
The build rejects mixed parser fingerprints from an interrupted vector update.

Qdrant receives a filter requiring both the selected document ID and membership
in the BM25 candidate IDs. An exact vector search ranks only those candidates by
cosine similarity using the stored E5 vectors. The claim is embedded once. BM25
scores are recorded for diagnosis but are not added to cosine scores; this is
embedding-based reranking, not score fusion or a cross-encoder.

## Limits and failure modes

- Missing/stale sparse index: run `sparse_index.py` after completing vector indexing.
- No lexical overlap: return zero candidates and skip dense search. A real claim
  run returns `NEUTRAL` with `status: no_evidence` without calling Apertus; a dry run
  records `empty_reason: no_lexical_matches`. There is no hidden dense fallback.
- The tokenizer supports DE/FR/IT characters, but BM25 does not translate synonyms
  or cross-language claims. Use matching claim/booklet languages for the first
  baseline, and measure this limitation explicitly.
- Small booklets or few matching passages can yield fewer than 50 candidates or
  five final passages. We never fill the pool with arbitrary zero-score passages.
- A relevant passage excluded by BM25 cannot be recovered by dense reranking.
- `--candidate-k` must be at least `--top-k`; Qdrant local mode still allows only
  one process to open the database folder at a time.
- No retrieval improvement is claimed until evaluated. The sparse build uses only
  source passages, not labels or gold evidence. Keep any tuning on development data.

To compare BM25 configurations, preserve the baseline directory and build another:

```sh
uv run python scripts/sparse_index.py --output data/bm25-experiment --k1 1.5 --b 0.75
```

Then use `--sparse-dir data/bm25-experiment` on the same development queries. Record
the split, candidate size and result, and reserve held-out data for final evaluation.

## Checkpoint and tests

```sh
uv run python -m unittest discover -s tests -v
```

The new tests check a hand-computed BM25 score, DE/FR/IT tokenization, one-chunk
corpora, deterministic candidate limits, JSON persistence, and changed/removed
chunks. Adapter tests use a fake Qdrant client and encoder to verify candidate-only
reranking, document isolation, no-match behavior and the dense baseline. They do
not substitute for running the new retrieval path against your actual Qdrant index.

Stop after comparing the two retrieval results for a known claim. Next evaluate
Recall@50 for candidate coverage and Recall@5 after reranking, separately from
Apertus classification accuracy. Deduplicate document/page pairs for page-level
gold evidence because long pages can have multiple chunks.
